## Step 1 — Real Task Registry + server-side telemetry capture
Make the registry a single source of truth derived from existing declarations, and capture a real record on every tool call.

- **`server/registry/taskRegistry.ts`** (new): a static `TASK_REGISTRY` derived by walking `TOOL_DECLARATIONS` so a tool can't exist in one place and not the other. Each entry: `{ name, category, description, clientSide, riskLevel, requiresConfirmation, version }`. Category is assigned from a mapping table keyed by tool name prefix. Exposes `getRegistry()`, `getTaskMeta(name)`, `listCategories()`.
- **`server/registry/metricsStore.ts`** (new): persisted metrics at `getDataDir()/task_metrics.json`. Appends one `TaskOutcome` per execution: `{ taskName, startedAt, durationMs, success, errorClass?, errorMessage?, recoveryTried?, recoverySucceeded?, confirmed }`. Persists via atomic write (tmp + rename). Provides: `recordOutcome()`, `getStats(taskName)`, `getAggregateStats()`, `computeConfidence(taskName)` (success-rate weighted over last N runs, with a sane prior so a brand-new task isn't 0%), `getAllStats()`. Bounded log (last ~1000 outcomes; cap file growth).
- **Wire into `server/tools/index.ts`**: wrap the body of `executeTool` so every call is timed with `performance.now()`; on success/failure call `recordOutcome()`. On caught error also call `analyzeError()` (real, from the refactored engine). This is the *single* place telemetry enters — no duplication.
- **No telemetry leak to Gemini**: metrics are stored/logged only; the function-response to Gemini stays unchanged.

## Step 2 — Fix the concrete bugs (evidence from audit)
1. **Double browser window on every search** (`index.ts:216-219`, `:296`): `searchGoogle`/`search_web` call both `openInDefaultBrowser(url)` (user Chrome) and `sandboxExec(research_topic)` (visible Playwright Chrome). Fix: when Playwright succeeds, **don't** also open the default browser — let the sandbox be the visible research window; open the default browser only as a *fallback* when Playwright is unavailable or returns nothing. (Default-browser-open stays the primary action for plain `open_website`/`searchYouTube`/`playFirstVideo` — only the Playwright+default double-open is removed.)
2. **Fake online check** (`systemInfo.ts:41`): replace the hardcoded `return true` with a real reachability probe (HTTP HEAD to a stable endpoint with a short timeout, cached briefly). Falls back to `false` on timeout/error.
3. **Dead/leaking safety branches** (`safety.ts`): `classifyRisk` references tools that don't exist (`delete_file`, `format_drive`, `install_software`, `make_purchase`, `run_terminal`, `send_email`, `uninstall_app`). Keep the *concept* (it's a reusable risk classifier), but: (a) tighten so it only emits HIGH for tool names/`file_operation` actions that actually exist, and (b) add the genuinely-HIGH real actions — `file_operation` delete/move/rename (already there) and the `set_volume`/`screenshot`-style are LOW. Add a unit test asserting the classifier matches the real registry.
4. **`commandProcessor` masks AI failures as success** (`commandProcessor.ts` outer catch returns `success:true`): when all models fail *and* AI was required, return `success:false` with a clear `output`. Fallback text still returned for display, but the flag must be honest so metrics/recovery aren't lied to.
5. **Electron swallows backend-spawn failure** (`main.cjs:39`): on spawn/require failure, surface a desktop `Notification` + log (currently silent). Pure additive guard, no behavior change on the happy path.

## Step 3 — Retry + recovery layer (the executor gets resilience)
- **`server/registry/recovery.ts`** (new): a small retry/recovery policy module keyed by task name and error *category* (Network / Missing Dependency / Permission / Timeout / Unknown — reusing the existing `ErrorCategory`).
  - `withRetry(taskName, fn, { retries })`: exponential backoff only for idempotent, non-destructive tasks and only on transient categories (Network/Timeout). Never retries HIGH-risk/destructive actions. Never retries `file_operation: delete` etc.
  - `getVerifiedFix(errorCategory)`: looks up previously-verified fixes from the (now real) error-intelligence store and returns the suggested strategy, so recovery can *attempt an alternate strategy* instead of blindly retrying — directly satisfying "never repeat the same failure blindly."
  - Records `recoveryTried`/`recoverySucceeded` into metrics.
- **Integrate into `executeTool`**: wrap the actual tool dispatch (the `switch`) in `withRetry`. The safety gate, speaker gate, and client-side forwarding stay *outside* retry (never retried, never double-confirmed).
- Specific known-recovery from the seed data, now made *real*: Playwright "Executable not found" → trigger `npx playwright install chromium` once then retry (guard against infinite reinstall). This replaces the fabricated `fix_1` with actual behavior.

## Step 4 — Real Self-Test / Health engine on startup
- **`server/registry/selfTest.ts`** (new): a `runHealthChecks()` that returns `{ checks: CheckResult[], summary }`. Each `CheckResult = { name, status: 'pass'|'fail'|'warn'|'skipped', detail, durationMs }`. Probes (all *side-effect-light*, none destructive):
  - `express_server` — already up by construction; sanity check.
  - `gemini_api_key` — env present.
  - `gemini_reachable` — optional short HTTP check (time-boxed; `skipped` if offline).
  - `powershell` — run a trivial `Write-Output` and assert exit 0.
  - `nircmd` — resolve path (download is lazy; we just check resolvability, not download).
  - `playwright` — `import('playwright')` resolves + chromium executable path exists; `warn` if missing with the exact fix command.
  - `data_dir_writable` — write/read/delete a probe file in `getDataDir()`.
  - `memory_store` — load + count ≥ default count.
  - `knowledge_index` — singleton loads, JSON parses.
  - `voice_profile` — `getVoiceprint()` present? (info, not a failure if absent).
  - `filesystem` (Node `fs`) — trivially pass.
- **Hook it in**: run on server start in `server.ts` (after listen, fire-and-forget, never block boot), expose results via a new `GET /api/health/detailed` (the existing static `/api/health` is kept for back-compat), and push a one-shot `status` WS message `type:'health', checks:[...]` so the client can show it. **Only subsystems that pass remain enabled** at the metric/dashboard level — surfaced as a health indicator, not by disabling code paths (the tools already degrade gracefully per-file).
